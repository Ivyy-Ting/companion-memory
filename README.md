# companion-memory：给 AI 角色的分层记忆

一套面向长期陪伴型 AI 角色的记忆方案：固定 prompt + 滚动压缩（Folio）+ 日总结向量索引 + 由小模型挑选的长期记忆召回，按缓存友好的顺序拼进每一轮请求。

本仓库包含设计说明和一份最小实现（约 500 行，只依赖 Python 标准库和任意 OpenAI 兼容接口）。实现是从一个长期运行的系统中提炼骨架重写的，不含原系统代码。

## 一条规矩：一样东西只干一件事

这套系统里出过的大毛病，追到底几乎都是同一个原因：一样东西同时担了两份差事。

| 一样东西兼着两件事 | 出了什么事 | 拆开以后 |
|---|---|---|
| 一条总结既当记忆，又当证据 | 总结写偏了没法核对；模型拿着总结里没有的细节"想当然"；当时的语气和心情被压成一句"她有点难过" | **总结只是索引，原话才是证据。** 总结指着它当初读的那几条原话，要细节就翻原话，对不上以原话为准 |
| 一个综合分既管"排第几"，又管"让不让进" | 重要的旧事分数高，跟什么话题都能挤进来 | **相关才能进，重要只管排队** |
| "被搜出来"就算"被用到" | 每次检索都给候选记"被翻起"，越翻越热：一条记忆被记了一千多次，其实大多是被拒的 | 只有真给了模型的才记一次 |
| 一条记忆装一整段时间（"某某一周合集"） | 什么话题都能撞上它 | 一条记忆只装一件事 |
| 存记忆的地方顺便决定该想起什么 | 规则怎么调都分不开相关和不相关 | 记忆库只负责找候选，挑哪几条交给单独的挑选者 |
| 身份设定（"我们怎么说话"）也存成记忆 | 和人设 prompt 各说各的，互相打架 | 身份归 prompt，记忆只管发生过的事 |

下面每一块都按这条规矩分工。

## 一张图

每一轮发给模型的请求，从上到下：

| 层 | 内容 | 变化频率 | 缓存 |
|---|---|---|---|
| 固定 prompt | 人设 + 规则 | 几乎不变 | ✅ |
| Folio 胶囊 | 旧对话压成的回忆段落 | 封新胶囊时才变 | ✅ |
| 最近原文 | 还没压缩的几轮原话 | 每轮多一点，前面不动 | ✅ |
| 本轮变化区 | 现在几点 + 召回的旧记忆 + 日总结召回 | 每轮都变 | ❌ |
| 当前输入 | 用户这一轮的消息 | — | — |

**不变的在前，变的在最后**。前面那几层每轮一字不差，prompt cache 能一直命中（实际运行中缓存读取率约 90%）。每轮变的东西全部塞进最后一条 user 消息，而且这条消息不存进历史，下一轮就不会把前缀弄乱。

## 四块记忆

### 1. 固定 prompt —— 他是谁

`prompt.md`。就是一份普通的 system prompt：人设、说话方式、规则。它永远放在最前面，不往里塞任何每轮会变的东西，连"现在几点"都不放。

"我们之间怎么说话"这类东西放这里，不要再存一份到记忆库：两份写法稍有不同，模型就不知道听谁的。

### 2. Folio —— 最近发生了什么（`memory/folio.py`）

对话越来越长，既不能全部放进上下文，也不能简单截断。Folio 把旧对话一段段压成"胶囊"：

- 未压缩的原文超过 6000 token、8 轮或 24 条，就把最老的几轮压成一段回忆；
- **最近 2 轮永远留原话**，刚发生的对话不应变成摘要；
- 胶囊块上限 7500 token，最新的优先；
- 胶囊块只在封新胶囊时变，所以缓存一直命中。

### 3. 日总结 —— 哪天发生了什么（`memory/day_summary.py`）

每天凌晨跑一次：

- 一天里隔 3 小时以上切成一段，每段写一份总结；
- **一件事一段，一段一个向量**（示例用 bge-m3），召回时拿到的就是一件完整的事；
- 每轮按相似度取 3 条（≥ 0.62），放进本轮变化区。

日总结是这套系统里"总结 ≠ 证据"做得最彻底的一块：

- 总结只是**索引**。模型想知道细节，用 `read_day(日期, 段号)` 翻回当天原话；
- 每份总结记下它是从**哪几条原话**写的（消息 id 范围）。以后当天补进消息、切段规则改了，`read_day` 翻到的仍然是这份总结当初读的那几句，不会张冠李戴；
- 总结和原话对不上，**以原话为准**。总结可以重写，原话不改；
- **情绪别交给摘要。** 摘要模型擅长记"发生了什么"，不擅长留住"当时是什么感觉"：一句带着哭腔的话，到总结里只剩"她有点难过"。要接住当时的心情，就翻原话，别让摘要替你转述。

### 4. 召回 —— 久远的事，什么时候该想起来（`memory/recall_gate.py`）

长期记忆库检索总会捞上来一堆候选，真正难的是**哪些该给模型看**。给多了，模型会把不相关的旧事扯进对话；给错了，模型会把无关内容当成确定的记忆说出来。

做法：**检索只管找候选，挑哪几条交给一个便宜模型。**

- 检索按排名取前 12 条候选，去掉最近 3 轮给过的、归档的、重复的；
- 把"助手上一句的结尾 + 用户这句 + 候选（每条 200 字）"交给一个小模型，让它回一个编号数组，比如 `[]` 或 `[2,5]`。标准写在 prompt 里：一个用心的伴侣此刻会不会自然想到这件事。偏好、习惯这类日常相关就选；只是撞了词、情绪相近不选；沉重的旧事除非正在谈同一件事，否则不选；
- 带上助手的上一句：用户说"那个呢"时，光看这一句不知道指什么；
- 最多 5 条；每条候选都记下 `fate`（选中 / 没选 / 最近给过 / 归档…），出了问题能查；
- 挑选者挂了就这一轮**一条都不给**，并告诉模型"查不了"。不退回阈值规则，因为阈值规则放进来的大多是错的；
- 给模型的每条记忆都带上出处（哪天第几段），模型要细节可以翻原话核对。

**为什么不用阈值。** 我们在原系统上标了 371 对"这句话 × 这条候选记忆"，比较了几种做法：

| 做法 | 放进来的里有几成是对的 | 该想起的捞回了几成 |
|---|---|---|
| 字面重合（两个中文双字词撞上就收） | 8% | 26% |
| 相似度 + 排名阈值（本仓库上一版） | 16% | 9% |
| 重排模型（bge-reranker-v2-m3） | AUC 0.6，基本分不开 | — |
| 便宜模型挑选（deepseek-v4-flash） | 约 50% | 约 80–90% |

挑选每轮多一次调用：约 1.4k token、0.8 秒左右，放在回复之前。

原系统先以"影子"方式跑：照旧用老规则，同时记下挑选者会选什么。真实对话里影子跑了 283 轮：

| | 字面规则（老） | 挑选者 |
|---|---|---|
| 放进来几条记忆 | 350 | 198 |
| 放得最多的那条 | 一段沉重旧事，52 次（几乎每个话题都撞上） | 同一条 0 次 |
| 出错 | — | 0（中位 0.8 秒，最慢 1.9 秒） |

对比之后切换成挑选者。建议你也这样上线。

**重要度不能当门槛。** 我们试过"重的记忆（重要度高、永久保存）门槛更高"：真正该想起的记忆里一半以上恰恰是重的。重要度、新近、未解决只能决定**相关的那几条排第几**，不能决定谁进来。

原系统的长期记忆库是 [Ombre Brain](https://github.com/P0luz/Ombre-Brain)（第三方项目，本仓库不含其代码）。`recall_gate` 不挑后端：任何能给出排名的检索都能接。demo 里直接拿日总结的向量当检索后端。

## 踩过的坑

以下问题都在原系统中实际出现过：

**召回**

- **别给所有被检索到的候选记"被翻起"。** 记忆库每次检索都给返回的候选加激活次数，包括随后被拒掉的。常被搜到的重记忆越来越热，分数越高越容易被搜到，一条记忆被记了一千多次。只给真正给了模型的那几条记。
- **别存"合集"式的长记忆。** 一条记忆写一周的事，跟什么话题都能撞上词。一件事一条。
- **挑选用的推理模型要关掉思考。** 不关的话，思考把 `max_tokens` 吃光，正文是空的。
- **普通聊天只发一条召回查询。** 发好几条宽泛查询，噪声会互相"佐证"，看起来像真相关。
- **当前这句别混进召回查询的上下文。** 记忆库把它当标题回显出来，模型就以为那是一段旧记忆。

**总结与压缩**

- **摘要别让模型输出 JSON。** 有一阵 DeepSeek 大约 12% 的 JSON 回复结尾会写坏。改成只要纯文本之后就没再坏过。（挑选者回的编号数组用正则宽松地抠，抠不到就当没回话。）
- **日总结的原文要围起来。** 不加 `<原始对话>` 并写明"不要接着往下写"，角色扮演的对话会被模型接着演下去。
- **相对时间要落成日期。** 胶囊里的"明天"如果不换成具体日期，几天后读起来就像一条新安排。
- **胶囊块别给太小。** 1800 token 只装得下忙碌一天里最后一小时的胶囊，现在是 7500。
- **压缩失败别永久停掉。** 连续失败就永久暂停，会让一次短暂的 503 变成几个小时无人察觉的停摆。改为冷却一段时间后自动重试。

**时间与缓存**

- **给模型本地时间，别给 UTC。** 给 UTC 时，模型把北京时间晚上 8:58 写成了"中午"，因为它看到的是 12:58Z。
- **时间戳只能来自消息本身。** 每轮现算"3 分钟前"会让历史每轮都变，缓存全废。"现在几点"只放在本轮变化区。
- **只给用户消息盖时间戳。** 回复也盖的话，模型会学着在回复开头写时间。
- **中文 token 用 字节/3 估。** 字数/4 会严重低估。

## 怎么跑

```bash
# 不联网的自检
python3 test_offline.py

# 用虚构对话跑一遍完整流程（需要两个接口，任何 OpenAI 兼容的都行）
export LLM_BASE_URL=https://api.deepseek.com/v1 LLM_API_KEY=... LLM_MODEL=deepseek-chat
export EMBED_BASE_URL=https://api.siliconflow.cn/v1 EMBED_API_KEY=... EMBED_MODEL=BAAI/bge-m3
python3 demo.py
```

demo 会打印每条候选记忆的去留、完整的请求（标出缓存断点）和角色的回复。

接到自己的项目里，大致是：

```python
from memory import store, folio, day_summary, recall_gate, layout, llm

store.add_message(db, conv, "user", text)
cands = 记忆库.search(text)                  # [{id, text, rank, ...}]
picked, ok = recall_gate.pick(text, cands, names, prev=上一句回复, recent_ids=最近给过的,
                              chat=便宜模型)
hits = day_summary.search(db, text)
msgs, _ = layout.build(prompt, folio.context(db, conv),
                       [recall_gate.render(picked, unavailable=not ok), day_summary.render(hits)], text)
reply = llm.chat(msgs)
store.add_message(db, conv, "assistant", reply)
folio.compress(db, conv, names)          # 放后台
# 每天凌晨：day_summary.summarize_day(db, conv, 昨天, names)
```

`chat` 可以传任何 `chat(messages, **kw) -> str` 的函数，挑选用的模型和聊天用的不必是同一个。

## 没带的东西

原系统中还有以下部分，本实现省略，需要时再加：

- 压缩失败的冷却和自动恢复、每日花费上限、备用线路；
- 手动编辑、钉住胶囊，以及修订历史；
- 消息分支（重新生成 / 编辑后的多个版本）；
- 长期记忆库本身（写入、情绪坐标、衰减、归档）。

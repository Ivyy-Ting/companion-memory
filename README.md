# companion-memory：给 AI 角色的分层记忆

一套面向长期陪伴型 AI 角色的记忆方案：固定 prompt + 滚动压缩（Folio）+ 日总结向量索引 + 带门槛的长期记忆召回，按缓存友好的顺序拼进每一轮请求。

本仓库包含设计说明和一份最小实现（约 500 行，只依赖 Python 标准库和任意 OpenAI 兼容接口）。实现是从一个长期运行的系统中提炼骨架重写的，不含原系统代码。

## 一张图

每一轮发给模型的请求，从上到下：

| 层 | 内容 | 变化频率 | 缓存 |
|---|---|---|---|
| 固定 prompt | 人设 + 规则 | 几乎不变 | ✅ |
| Folio 胶囊 | 旧对话压成的回忆段落 | 封新胶囊时才变 | ✅ |
| 最近原文 | 还没压缩的几轮原话 | 每轮多一点，前面不动 | ✅ |
| 本轮变化区 | 现在几点 + 召回的旧记忆 + 日总结召回 | 每轮都变 | ❌ |
| 当前输入 | 用户这一轮的消息 | — | — |

**不变的在前，变的在最后**，这是整套设计的核心。前面那几层每轮一字不差，prompt cache 能一直命中（实际运行中缓存读取率约 90%）。每轮变的东西全部塞进最后一条 user 消息，而且这条消息不存进历史，下一轮就不会把前缀弄乱。

## 四块记忆

### 1. 固定 prompt —— 他是谁

`prompt.md`。就是一份普通的 system prompt：人设、说话方式、规则。它永远放在最前面，不往里塞任何每轮会变的东西，连"现在几点"都不放。

### 2. Folio —— 最近发生了什么（`memory/folio.py`）

对话越来越长，既不能全部放进上下文，也不能简单截断。Folio 把旧对话一段段压成"胶囊"：

- 未压缩的原文超过 6000 token、8 轮或 24 条，就把最老的几轮压成一段回忆；
- **最近 2 轮永远留原话**，刚发生的对话不应变成摘要；
- 胶囊块上限 7500 token，最新的优先；
- 胶囊块只在封新胶囊时变，所以缓存一直命中。

### 3. 日总结 —— 哪天发生了什么（`memory/day_summary.py`）

每天凌晨跑一次：

- 一天里隔 3 小时以上切成一段，每段写一份总结；
- **一件事一段，一段一个向量**（示例用 bge-m3），召回时拿到的就是一件完整的事；
- 每轮按相似度取 3 条（≥ 0.62），放进本轮变化区；
- 日总结只是**索引**：模型想知道细节，用 `read_day(日期, 段号)` 翻回当天原话。总结会丢细节，原话不会。

### 4. 召回门槛 —— 久远的事，什么时候该想起来（`memory/recall_gate.py`）

长期记忆库检索总会捞上来一堆候选，真正难的是**哪些该给模型看**。给多了，模型会把不相关的旧事扯进对话；给错了，模型会把无关内容当成确定的记忆说出来。

规则：

- **必须有语义证据**。新近、重要、常被翻起——这些都不能单独让一条记忆变成"相关"；
- 四种放行方式：
  - 字面有重合 + 向量也站得住（HYBRID）
  - 字面有重合 + 相似度 ≥ 0.60 且排前 5（LEXICAL）
  - 向量排前 2 且相似度 ≥ 0.62（VECTOR）
  - 只靠"第一名甩开第二名 0.08"（MARGIN）—— 最容易误召，默认关
- 最多 5 条；最近 3 轮已经给过的不再给；归档的记忆在日常聊天里不复活；
- 每条候选都记下"为什么收 / 为什么拒"，出了问题能查；
- "没找到"和"记忆服务挂了"分开告诉模型，不然它会把服务挂了当成没这回事。

这些阈值来自原系统数据上的离线评测（带留出集）。**换了 embedding 模型或者数据差别很大，请自己重新校准。**

原系统的长期记忆库是 [Ombre Brain](https://github.com/P0luz/Ombre-Brain)（第三方项目，本仓库不含其代码）。`recall_gate` 不挑后端：任何能给出"相似度 + 排名"的检索都能接。demo 里直接拿日总结的向量当检索后端。

## 踩过的坑

以下问题都在原系统中实际出现过：

- **摘要别让模型输出 JSON。** 有一阵 DeepSeek 大约 12% 的 JSON 回复结尾会写坏。改成只要纯文本之后就没再坏过。
- **给模型本地时间，别给 UTC。** 给 UTC 时，模型把北京时间晚上 8:58 写成了"中午"，因为它看到的是 12:58Z。
- **相对时间要落成日期。** 胶囊里的"明天"如果不换成具体日期，几天后读起来就像一条新安排。
- **胶囊块别给太小。** 1800 token 只装得下忙碌一天里最后一小时的胶囊，现在是 7500。
- **日总结的原文要围起来。** 不加 `<原始对话>` 并写明"不要接着往下写"，角色扮演的对话会被模型接着演下去。
- **时间戳只能来自消息本身。** 每轮现算"3 分钟前"会让历史每轮都变，缓存全废。"现在几点"只放在本轮变化区。
- **只给用户消息盖时间戳。** 回复也盖的话，模型会学着在回复开头写时间。
- **压缩失败别永久停掉。** 连续失败就永久暂停，会让一次短暂的 503 变成几个小时无人察觉的停摆。改为冷却一段时间后自动重试。
- **当前这句别混进召回查询的上下文。** 记忆库把它当标题回显出来，模型就以为那是一段旧记忆。
- **普通聊天只发一条召回查询。** 发好几条宽泛查询，噪声会互相"佐证"，看起来像真相关。
- **中文 token 用 字节/3 估。** 字数/4 会严重低估。

## 怎么跑

```bash
# 不联网的自检
python3 test_offline.py

# 用虚构对话跑一遍完整流程（需要两个接口，任何 OpenAI 兼容的都行）
export LLM_BASE_URL=https://api.deepseek.com/v1 LLM_API_KEY=... LLM_MODEL=deepseek-chat
export EMBED_BASE_URL=https://api.siliconflow.cn/v1 EMBED_API_KEY=... EMBED_MODEL=BAAI/bge-m3
python3 demo.py
```

demo 会打印每条候选记忆的去留、完整的请求（标出缓存断点）和角色的回复。

接到自己的项目里，大致是：

```python
from memory import store, folio, day_summary, recall_gate, layout, llm

store.add_message(db, conv, "user", text)
hits = day_summary.search(db, text)
msgs, _ = layout.build(prompt, folio.context(db, conv),
                       [recall_gate.render(...), day_summary.render(hits)], text)
reply = llm.chat(msgs)
store.add_message(db, conv, "assistant", reply)
folio.compress(db, conv, names)          # 放后台
# 每天凌晨：day_summary.summarize_day(db, conv, 昨天, names)
```

## 没带的东西

原系统中还有以下部分，本实现省略，需要时再加：

- 压缩失败的冷却和自动恢复、每日花费上限、备用线路；
- 手动编辑、钉住胶囊，以及修订历史；
- 消息分支（重新生成 / 编辑后的多个版本）；
- 长期记忆库本身（写入、情绪坐标、衰减、归档）。
